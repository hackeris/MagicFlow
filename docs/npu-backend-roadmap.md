# PyTorch NPU 后端路线(NNRt)

> 2026-09-11 定稿。**目标定位:把 NPU 用起来** —— 打通 PyTorch → 鸿蒙 NPU 的执行通路,
> 建立可复用的软件栈与基准数据,为后续接入更强的 NPU 硬件做准备。
> **不以加速比为验收门槛**(用户 2026-09-11 拍板:「先不在乎快慢,为后续接入更强的
> NPU 做准备」)。一条软性底线:NPU 路径不应慢到失去调试价值(建议 ≤ 3× CPU 用时)。

## 0. 已确立的事实(勿重查)

| 事实 | 依据 |
|---|---|
| NNRt 在线构图可用,SD 链 34 算子 **33 通过** | poc/npu CH-02(9030,2026-09-11 复跑一致) |
| 离线模型(自定义算子)被系统库**显式拒绝** | CH-04,build rc=1,两设备复现 |
| 单算子直调**无接口**,MindSporeLite 仅 ArkTS | CH-05 / CH-07 |
| **NCP 子进程内可完整执行**(构图→rtSetDevice→Build→RunSync) | CH-06 全链 PASS,2026-09-11 |
| 单算子开销:编译 3~4 ms、执行 0~1 ms | CH-03 |
| 目标机 1.5 = MOR-M1 / KirinXE90 / 24GB / 192.168.1.5:44959 | — |

技术路线因而是**唯一的**:PyTorch PrivateUse1 后端插件(注册 `cann` 设备)→ 热算子走
NNRt 在线构图 → 其余算子自动回落 CPU(OpenBLAS)。不改动 skh 预编译栈(只做扩展)。

## 1. 总体路线

| 阶段 | 内容 | 验收判据 | 预估 |
|---|---|---|---|
| **P0 打通** | 自建 torch C++ 扩展在设备上可加载;注册最小 PrivateUse1 设备 | 设备上 `import` 成功、`torch.cann.is_available()` 为 True、能建 cann 张量 | 2~3 天 |
| **P1 最小闭环** | allocator / device guard / 3 个算子(CONV2D、MATMUL、SOFTMAX)+ CPU fallback | 真机子进程内数值对拍通过(NPU vs CPU 相对误差 < 1e-3);未实现算子自动回落 | 1~2 周 |
| **P2 端到端** | 按实测算子分布补覆盖;SD-Turbo 256×256 走 NPU 出图 | 出图成功 + 与 CPU 版 SSIM > 0.85 + **逐算子走向与耗时数据落盘** | 3~5 周 |
| **P3 就绪化** | 打包进 HAP、开关与回退、基准报告、文档 | 主项目可选启用(默认仍走 CPU);同机 CPU/NPU 双路可切换 | 1 周 |

**性能数据的采集贯穿全程**(每阶段必须留档),但不作为通过与否的门槛 —— 它的用途是
"未来换更强 NPU 时,同一套基准直接复测出代际差"。

## 2. 面向"更强 NPU"的架构原则

**前提:目标硬件是同体系的下一代(麒麟新芯片 / 同一 NNRt 接口),不是换运行时**
(用户 2026-09-11 明确)。因此不做"可换后端"的过度抽象 —— 那只会凭空增加间接层;
准备工作的重心是**让升级只改数据、不改代码**:

1. **薄封装,专注 NNRt**:不为假想的其他运行时留接口;但 NNRt 调用集中在薄薄一层内,
   便于下一代接口若有变化时集中修改。
2. **能力靠探测,不靠假设**:设备选择、算子支持度、限制(如 HIAI_F 虚拟口不可用)一律
   运行时探测。下一代芯片的设备名、算子集、限制都可能变 —— 写死 9030 特性是最大的升级债。
3. **算子映射数据驱动**:算子 → NNRt 的映射是一张表;下一代多支持一个算子,改表即可,
   回落 CPU 的清单随之自动更新。
4. **可观测优先**:每个算子的走向(NPU / 回落 CPU)+ 编译/执行耗时 —— 换芯片时同一套
   基准复测,代际差直接可见。这是本路线最核心的交付资产,先于性能本身。
5. **可回退**:CPU 路径永远可用,开关默认关闭;任何阶段都能一键回到现状。

## 3. 关键设计点(实施时必须正面处理)

- **CPU fallback 第一天就要有**:`TORCH_LIBRARY_IMPL(_, PrivateUse1, m)` 注册 fallback,
  未实现算子自动走 CPU —— 这是"任何工作流都能跑"的保险,也避免调试期被单点算子卡死。
- **executor 缓存**:同一算子的图在每步推理中完全相同,按 (算子类型, 形状, 参数) 缓存已编译
  executor、只重绑输入输出张量。NNRt 自身的模型缓存**不会**降低 Build 耗时(实测 3~4ms 恒定),
  收益必须靠复用拿。
- **权重常驻**:模型权重一次性转 FP16 驻留 NPU,每步只搬运激活。
- **精度对齐**:FP16 权重对 SSIM 的影响必须实测(P2 判据的一部分)。
- **算子清单按实测排**:开工先跑 profiler 统计一次 SD-Turbo 推理实际调用的 aten 算子与频次,
  按频次实现;不照 34 算子表盲铺。

## 3.5 P1 实施定谳(2026-09-12, 已交付)

一键验证: `bash nnrt-backend/scripts/verify_nnrt_p1.sh [--rebuild]`
（删产物从零重建 + 真机全链 + 判据断言, 已演练通过）

**已打通**
- PrivateUse1 骨架: `NnrtAllocator`/`NnrtGuardImpl`/`NnrtHooks` + `rename_privateuse1_backend("nnrt")`
- `aten::mm` 下沉 NNRt(MATMUL), 数值正确; `aten::matmul` 经 composite polyfill 到 `mm` 同样正确
- 未下沉算子走 fallback 回 CPU —— 关键是 `op.redispatchBoxed(DispatchKeySet(DispatchKey::CPU), stack)`,
  **不能**用 `ExcludeDispatchKeyGuard + callBoxed`(必卡)

**⚠ 精度实况(与直觉相反, 决策必读)**
9030 的 NNRt MATMUL 在 **fp32 声明下实际按 fp16 计算**:
用 fp16 可精确表示的输入(0.5×0.25)得**零误差**; 随机 fp32 输入被舍入 →
mean 相对误差 7e-4~1.2e-3、max ~1e-2, **且与 K 无关**(K8 甚至大于 K64 ⇒ 非累加损失)。
故数值判据为 `mean < 5e-3`, **不能**按 fp32 的 1e-6 要求。SD 级出图对该量级噪声鲁棒。

**⚠ 两条踩坑(已写进代码注释与验证脚本头)**
1. **NNRt 编译缓存会串图**: 同一 `cacheDir` 下, 它把别的图的编译结果交给当前图 —— 实测
   P1-a 的 ADD 图(shape `[1,2,2,3]`)污染了 MATMUL, 执行器报出 `[1,2,2,3]`、输出恒为
   `2.0`(=1.0+1.0)。**修法: 按图签名(张量登记顺序×dtype×rank×shape×type)+性能模式分子目录**。
   ⚠ `poc/npu` 的"33 项输出数值全部正确"为何没发现它? —— 它的 `op_run` **把所有输入(含 weight)
   统一填 1.0**, PASS 判据只看 `rcGraph/rcBuild/rcRun`, 数值仅打印前 4 个供人工核对。
   **全 1 数据下"对的答案"与"顺序/布局出错的答案"恰好相同**(求和与元素次序无关) ⇒ 天然盲区。
   教训: **用例必须让"错的答案" ≠ "对的答案"**; 全 1 数据、对称尺寸(kH=kW=inC)都是无效判别数据。
   ("执行成功 ≠ 算得对"; 反过来说, "数值对得上"也只在数据有区分度时才算证据。)

   **⚠ 2026-09-12 复核定谳: `poc/npu` 的"33/34 PASS"应整体作废** —— 回到原始报告逐行核对,
   四条同时成立即可确诊为缓存串图: ①头行写明输入是 `1.0-filled`, 但 **34 项输出全是 `2.00`**
   (SUB 应为 0、DIV/POW 应为 1、LOG/SQRT/TANH 不可能等于 2); ②执行器张量形状**一律是
   `[1,2,2,3]`**(第 0 项 ADD 的图); ③耗时**只有 ADD 是 `build=0(24ms)`** 真实编译, 其余
   3~4ms 全为缓存命中; ④`[ex:1/2]` 输入数也全都一样。⇒ **后 33 项复用了 ADD 的编译产物**,
   **CH-02 实际只证明 ADD 一个算子真实可用**。(CH-06 的 `out[0]=2.00` 是 ADD 图, 2=1+1
   正确, 那条仍达标。)
2. **model 所有权必须单方持有**: 算子函数与 `Runner` 析构都销毁同一个 model → `comfy_child`
   在 `execRun` 之后静默死亡, 日志停在 kernel 最后一行, **伪装成"卡死"**(存活判据又只看主应用
   进程, 连掩盖三轮)。现约定: **model 归创建它的算子函数独占销毁**, `Runner` 析构只清 exec/comp。

## 4. 风险与备选

| 风险 | 应对 |
|---|---|
| P0 失败(扩展 ABI / libc++ 双命名空间) | 退 **Plan B:算子级替换** —— ctypes 直调 NNRt 替换少数热算子,不碰 PyTorch 内部;能拿到大部分收益但侵入性强 |
| 算子覆盖面不足(attention 等复杂算子) | fallback 兜底;按 profiler 数据决定投入顺序,长尾不追 |
| 慢到不可用(负优化) | 记录数据、设软性底线;必要时只让卷积类走 NPU |
| 下一代芯片的接口/算子集有变 | 能力探测 + 映射表数据驱动(第 2 节);NNRt 调用集中在薄封装层,便于集中修改 |
