# 本地推理 R1: torch 并行不生效调查(证据集)

**日期**: 2026-09-04  **状态**: 定谳(证据全闭环)  **结论**: 不是"torch 不支持并行"——这个 OHOS 构建把 BLAS 选成了 **Eigen(单线程)**,torch 的
`set_num_threads` 从不作用于 Eigen-GEMM;修复 = 重编换 `USE_BLAS=OpenBLAS`(skh 发行树自带 `libopenblas.a+头`)。

---

## 1. 现象(设备实测,可复现)
- `torch.get_num_threads() = 1`(初始);`oset_num_threads(12)`/`omp_set_num_threads(12)` 后 `get_num_threads() = 12` ✔ 配置层可调
- **op 层不变**: `matmul(2048×2048)×4 = 8.979s`(≈3.8 GF/s = 单核水平;n=12 时同样 8.98s)
- 全流程 CPU 采样: 加载期/KSampler 期均 ~0.9-1.2 核(41 线程存在但 op 不并行)

### 2.3 运行时 libomp 健康(空口不说)
- `readelf -d libtorch_cpu.so` NEEDED 含 `libomp.so`; `libomp.so` SONAME=`libomp.so`(匹配); 1.23MB 全符号(`omp_get_max_threads`/`omp_set_num_thredeadth` 等)
- 探针 `ctypes.CDLL("libomp.so")`: 初始 `max=1 num=1 procs=8`;`omp_set_num_threads(6)` 后 `max=6` → 库本身可调、无 stub
- `.so` strings: 只有 `"ATen parallel backend: "` + `"OpenMP"` 分支(无 `"native thread pool"`)→ 编译态后端=OpenMP

### 2.4 早期快照时序(为何 init=1)
- `OMP-DIRECT max=1`(首测)且 env=12——libomp 首次初始化发生于**早期 env 单化(历史 run37 段,与本轮改动互见)时刻**;env 后改无效
- **与 op 单线程无关**:op 层瓶颈=Eigen-GEMM(2.2);init 快照只解释"配置默认 1"

### 2.5 修复弹药存在
```
研究区/正规区 skh 树: skh-run/usr/lib/libopenblas.a + skh-run/usr/include/openblas/
```
→ 重编 torch 时 `USE_BLAS=OpenBLAS` 即可(其余 cmake 配置不变,skh SDK 链现成)。

## 3. 结论与修复选项
- 修复 A'(推荐,预期好): 复刻 skh build.sh,改 `-DUSE_BLAS=OpenBLAS -DBLAS=OpenBLAS` 重编 torch → 12 核 GEMM,512×4 预期 3-6 分钟,再实测复核。
- 修复 C(当前可用): 单线程下轻模型(<1GB)5-20s/图可体验。
- 其他候选(未探): mobile-式 threadpool(USE_PTHREADPOOL)与 `THREADPOOL` backends 的切换,如 A' 不达预期再评估。

## 6. G4 定谳(2026-09-05): OpenBLAS 12 线程实弹成功

**状态**: RI 结论"Eigen 单线程"已修复,重编换 OpenBLAS 后真机实测**多线程 GEMM 生效,出图成功**。

### 6.1 装载死亡链三连环(全部实锤,根治)
| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | dlopen 即 SIGSYS(31)@syscall 235 | OpenBLAS `my_mbind` syscall 232/235 被 OHOS seccomp 绝杀,init 段 `gotoblas_init→blas_thread_init→blas_memory_alloc` 即死 | 补丁 13: `common_linux.h` `__OHOS__` 分支 no-op |
| 2 | dlopen NULL errno=22 | torch 静态吸取 openblas 时 **60 个 LAPACK F77 符号缺失**(NO_LAPACK=1 或仅 C 级 lapack 产物)、musl BIND_NOW 即时报错 | **完整 Fortran-LAPACK**(交叉 gfortran 纯 .o) |
| 3 | 最后 1 个未定义 `_gfortran_concat_string` | gfortran runtime 字符串拼接,错误路径引用 | 独立 stub .c(`gfortran_concat_stub.c`)编进库 |

**判据**: 新 libtorch_cpu.so(203,389,344B)与已知可装载 OK 版未定义符号 **差=0** → 真机 `PROBE-DLOK` ✓

### 6.2 构建血泪(已固化进 `thirdparty/ohos-torch/build_openblas_ohos.sh` 头注)
- make 并行 `-j libs netlib` **ar 竞态撕裂库**(对象变全零)→ 必须顺序
- 全套工具链参数(CC/AR=llvm-ar/RANLIB=llvm-ranlib/NM=llvm-nm)— 漏传=宿主 cc 混入 x86 对象
- `make clean` 不清 Makefile.conf;增量 `ar -u` 永久保留首次错误对象 → 全清+一次性编译
- **grep -q 进管道 = SIGPIPE 前导**(命中即关 stdin → 上游 nm 141 → pipefail 误判 FATAL)→ 用非 -q

### 6.3 OpenMP 关键 pivot(pthread→OPENMP)
真机 512×4 首跑 15 分钟无产出 + diag.log 刷屏 `OpenBLAS Warning: Detect OpenMP Loop and this application may hang`:
torch 侧 libomp 并行区(attention/conv 的 `parallel_for`)内部再调 pthread 版 OpenBLAS → OpenBLAS 拒绝并行/降级。
**修复**: OpenBLAS `USE_OPENMP=1`,与 torch 共用 libomp 运行时(`GOMP_*` 由 HAP libs/libomp.so 提供,已验证)。新进程段 Warning=0。
